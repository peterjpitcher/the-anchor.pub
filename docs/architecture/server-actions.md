## Why API routes, not server actions

1. **`ANCHOR_API_KEY` must stay server-side.** Every mutation eventually calls `management.orangejelly.co.uk` with that key in an `X-API-Key` header. A discrete proxy route gives one obvious place to attach (and audit) the key. Server actions would inline that responsibility into client components and complicate review.
2. **CORS, idempotency, and headers are explicit.** Booking creation (`app/api/table-bookings/route.ts`) generates an `Idempotency-Key`, forwards a Turnstile token via `x-turnstile-token`, and shapes the upstream JSON. Doing this in a route handler keeps the contract obvious and testable (`app/api/table-bookings/__tests__/route.test.ts`).
3. **Caching can be set in middleware.** `middleware.ts` applies `s-maxage=60, stale-while-revalidate=300` to most `/api/*` responses and `no-store` to `/api/business/hours`. Server actions bypass that path.
4. **External callers (AI agents) need a stable HTTP contract.** `app/api/booking/agent/route.ts` is consumed by GPT-5 and similar clients. A server action would not be reachable.
5. **Simpler testing.** Each route can be exercised with `NextRequest` fixtures in Jest (see `app/api/**/__tests__/`).
