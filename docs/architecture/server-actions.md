### Rationale

The Anchor website proxies all mutations through **HTTP API routes** instead of Next.js Server Actions. This architectural choice provides:

1. **Explicit auth control**: API key validation happens in route handlers, not transparently in server actions
2. **Visibility**: HTTP routes are easier to audit, debug, and understand than hidden server-side functions
3. **Flexibility**: API routes can implement complex middleware, caching, and error handling
4. **API consistency**: The same endpoints power both the website and potentially external integrations

## Why Not Server Actions?

While Server Actions would simplify the code in some cases, the current HTTP route approach is **intentional** and aligns with the project's design:

1. **This website is API-first**: It proxies to a separate management system. Server Actions are best when the server action directly owns the data model. Here, the management API owns everything.
2. **Auth is explicit**: API key validation is visible in each route, not hidden in action.ts files.
3. **Error handling is clear**: HTTP status codes + error objects are clearer than exceptions in server actions.
4. **Testing is simpler**: HTTP routes can be tested like any API endpoint.

## If Server Actions Were Added

- `app/actions/enquiries.ts` — Enquiry form submissions

However, the current architecture (HTTP routes) is **working well** and aligns with the project's multi-API integration philosophy.
