# Technical SEO Audit Report -- The Anchor

**Date:** 22 March 2026
**Auditor:** Technical SEO Specialist (Phase 2)
**Site:** https://www.the-anchor.pub
**Scope:** Full technical audit of codebase and live site

---

## Executive Summary

The Anchor's technical SEO foundation is solid for a Next.js pub website -- the site returns proper HTTP status codes, has HSTS enabled, uses structured data, and has canonical tags on almost every page. However, several systemic issues are limiting performance: Cloudflare's managed robots.txt is blocking all major AI crawlers (including ClaudeBot and GPTBot), duplicate viewport meta tags are rendered on every page, 27 out of ~100+ pages have BreadcrumbList schema (leaving 75%+ without), EventSeries schemas are defined but only deployed on 4 pages, the `keywords` meta tag is present on nearly every page (wasted bytes since Google ignores it), and multiple cannibalisation targets remain in the sitemap with self-canonicals. Fixing these issues requires mostly template-level changes that cascade across the entire site.

**Overall Technical SEO Score: 7/10** (up from initial 7/10 -- improvements made but systemic issues persist)

## 1. Critical Issues

### CRIT-1: Cloudflare Managed Robots.txt Blocks All AI Crawlers

**What:** The live `robots.txt` at `https://www.the-anchor.pub/robots.txt` contains Cloudflare-injected directives that block GPTBot, ClaudeBot, Amazonbot, Google-Extended, Bytespider, CCBot, Applebot-Extended, and meta-externalagent -- all with `Disallow: /`.

**Evidence (live robots.txt):**
```
# BEGIN Cloudflare Managed content
User-agent: ClaudeBot
Disallow: /

User-agent: GPTBot
Disallow: /

User-agent: Google-Extended
Disallow: /
# END Cloudflare Managed Content
```

**Why it matters:** The strategy document (Pillar 6) explicitly calls for AI search optimisation. The existing `llms.txt` file becomes worthless if AI crawlers cannot access the site. Perplexity, ChatGPT, and Google AI Overviews will not cite The Anchor if their crawlers are blocked. This directly contradicts the strategy target of "Consistent AI search citations for core queries."

**How to fix:** In Cloudflare Dashboard > Settings > Scrape Shield (or AI section), disable or customise the managed AI bot blocking. Specifically allow: GPTBot, ClaudeBot, Applebot-Extended, Google-Extended. Keep blocking: Bytespider, CCBot (if desired for training-only bots).

**Impact:** High -- enables entire AI search strategy pillar
**Effort:** 5 minutes (Cloudflare dashboard change)

---

### CRIT-2: Duplicate Viewport Meta Tags on Every Page

**What:** The rendered HTML contains two identical `<meta name="viewport">` tags:
```html
<meta name="viewport" content="width=device-width, initial-scale=1"/>
<meta name="viewport" content="width=device-width, initial-scale=1"/>
```

**Source:** One is auto-generated by Next.js from the `metadata` export in `app/layout.tsx`. The second is the manual `<meta name="viewport" .../>` tag on line 186 of `app/layout.tsx`.

**File:** `/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/layout.tsx`, line 186

**Why it matters:** While browsers handle this gracefully, it is a validation error that signals technical sloppiness to search quality raters. Google's Core Web Vitals tools flag duplicate meta tags.

**How to fix:** Remove the manual viewport meta tag from the `<head>` block in `app/layout.tsx` (line 186). Next.js automatically generates this from the metadata API.

**Impact:** Low-Medium (clean HTML, passes validation)
**Effort:** 1 minute

### CRIT-3: Cannibalisation Targets Still in Sitemap with Self-Canonicals

**What:** Pages identified as cannibalisation targets in the opportunity map are still present in the sitemap and self-canonicalise, telling Google to keep indexing both competing pages:

| Cannibalising pair | Both in sitemap? | Both self-canonical? |
|---|---|---|
| `/pub-garden-heathrow` vs `/beer-garden` | Yes | Yes |
| `/private-party-venue` vs `/private-hire` | Yes | Yes |

**Files:**
- `/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/sitemap.ts` (lines 119, 160)
- `/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/pub-garden-heathrow/page.tsx` (line 29: `canonical: '/pub-garden-heathrow'`)

**Why it matters:** Google sees two pages competing for the same query with equal signals. Link equity is split. The strategy explicitly calls for 301 redirects from `/pub-garden-heathrow` to `/beer-garden` and from `/private-party-venue` to `/private-hire`.

**How to fix:**
1. Add 301 redirects in `config/redirects/additional-redirects.json`
2. Remove `/pub-garden-heathrow` and `/private-party-venue` from sitemap static routes
3. Eventually remove the page files (after redirect is confirmed working)

**Impact:** Medium -- consolidates authority on target pages
**Effort:** 15 minutes

## 2. Crawlability & Indexation

### 2.1 Robots.txt

**Status:** Partially correct but compromised by Cloudflare overlay

**Codebase (`app/robots.ts`):** Well-configured. Blocks `/api/`, internal debug routes, `/_next/data/`, test pages. Includes sitemap reference.

**Live output:** The Next.js-generated robots.txt is present but preceded by Cloudflare's managed block which adds the AI crawler blocks and Content-Signal directives. The two `User-agent: *` blocks may cause parser confusion in simpler crawlers -- the first (Cloudflare-managed) says `Allow: /` and the second (Next.js-generated) provides the detailed disallow list.

**Issues:**
1. **Two `User-agent: *` blocks** -- some crawlers may only parse the first one, missing the disallow rules entirely
2. **AI crawler blocking** -- see CRIT-1 above
3. **Cache TTL is 24 hours** (set in `next.config.js` line 128: `max-age=86400`) -- acceptable but strategy document suggests reducing

**Recommendations:**
- Resolve the Cloudflare/Next.js robots.txt conflict (see CRIT-1)
- Consider reducing cache TTL to 3600 (1 hour) for faster propagation of changes

### 2.2 XML Sitemap

**Status:** Good -- dynamic, comprehensive

**File:** `/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/sitemap.ts`

**What works:**
- Covers all static routes (~100 pages)
- Dynamically includes blog posts, tag pages, event pages, landmark pages
- Filters out draft events, excluded blog slugs, noindex posts, redirect-source tags
- Sets appropriate priority levels (homepage 1.0, book-table 0.95, etc.)
- Revalidates hourly

**Issues:**
1. **Static `lastModified` date** (line 70): All static routes use `STATIC_LAST_MODIFIED = new Date('2026-03-20')`. This provides no meaningful signal to Google about when individual pages actually changed. Every time the sitemap is regenerated, all pages report the same date.
2. **Cannibalisation targets in sitemap** -- `/pub-garden-heathrow` and `/private-party-venue` should be removed (see CRIT-3)
3. **`/pubs-in-stanwell`** is NOT in the sitemap (correctly excluded) but the page still exists and self-canonicalises at `/pubs-in-stanwell`. It should be redirected to `/stanwell-pub`.
4. **Missing pages in sitemap:** `/free-parking`, `/book-event`, `/whats-on/drag-shows` exist as pages but are not in the sitemap. Verify if these should be indexed or noindexed.
5. **Event sitemap fetches from API** -- if the management API is down, event pages silently disappear from the sitemap (the `catch` block returns `[]`). No logging or alerting.

### 2.3 Canonical Tags

**Status:** Good -- systematic implementation

Almost all public pages have explicit canonical tags via `alternates: { canonical: '/path' }`. The root layout correctly sets only `metadataBase` without a root-level canonical (avoiding the past bug documented in CLAUDE.md).

**Issues:**
1. **`/private-hire/near/[slug]` pages have NO canonical tag** -- these landmark-based pages (crematoriums, registry offices, etc.) are missing canonicals entirely. File: `/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/private-hire/near/[slug]/page.tsx`.
2. **`/drinks/[slug]` pages have no canonical** -- the dynamic drinks pages lack canonical tags.
3. **`/whats-on/drag-shows` has no canonical** -- orphaned sub-page.
4. **Self-canonicals on cannibalisation targets** -- `/pub-garden-heathrow` canonicals to itself rather than to `/beer-garden` (the canonical target). Same for `/private-party-venue`.

### 2.4 Indexation Signals

**Status:** Good

- Debug/test pages use `head.tsx` files with `<meta name="robots" content="noindex,nofollow" />`
- Blog posts support `noindex` frontmatter flag, correctly propagated to metadata
- `/leave-review` is noindexed (correct -- utility page)
- `/parking/bookings/[id]` is noindexed (correct -- transactional page)
- Root layout sets proper `robots` and `googleBot` directives with `max-image-preview: large`

**Issue:** Test/debug pages use the legacy `head.tsx` pattern for noindex rather than the `metadata` export. While functional, this is inconsistent with the rest of the codebase. Low priority to fix.

### 2.5 Redirect Handling

**Status:** Comprehensive but potentially slow

**Total redirect rules:** ~560 across 6 JSON files (3,384 lines total)
- `wix-redirects.json`: 792 lines (legacy Wix migration)
- `blog-redirects.json`: 992 lines (blog URL changes)
- `tag-redirects.json`: 697 lines (tag consolidation)
- `additional-redirects.json`: 489 lines
- `drinks-redirects.json`: 382 lines
- `legacy-redirects.json`: 32 lines

The `normaliseRedirect()` function in `next.config.js` correctly converts `permanent: true` to `statusCode: 301`.

**Issues:**
1. **Volume concern:** 560+ redirects are loaded on every request by Next.js. While Vercel caches these at the edge, the configuration size could slow build times.
2. **No audit for redirect chains:** The strategy document calls for auditing redirect chains. With 560+ rules, chain redirects (A -> B -> C) are likely. No automated check exists.
3. **Missing redirects for cannibalisation targets:** `/pub-garden-heathrow` -> `/beer-garden`, `/private-party-venue` -> `/private-hire`, `/pubs-in-stanwell` -> `/stanwell-pub` are not yet implemented.

## 4. Performance & Core Web Vitals

### 4.1 Image Optimisation

**Status:** Good

- Next.js `<Image>` component used consistently with proper `sizes` attributes
- Image formats: AVIF and WebP configured in `next.config.js` (line 226)
- Image caching: 1-year TTL (line 229)
- Remote images allowed from management API domain and Supabase storage
- Hero images use `fetchPriority="high"` and `priority` prop

**Issue:** Logo image is preloaded in two different sizes (120px and 150px) on the homepage -- both for desktop and mobile layouts. This means mobile users download preload hints for a desktop-only image size and vice versa. Visible in the live HTML output.

### 4.2 JavaScript & Bundle

**Status:** Acceptable with some concerns

- GTM loaded as render-blocking inline script in `<head>` (line 164-171 of layout.tsx)
- Three dynamic imports use `ssr: false` to avoid hydration cost: `EventCountdownBanner`, `ChristmasLightbox`, `PrivateHire2026PromoGate`
- `DeferredRender` component delays non-critical UI
- Console removal in production via SWC compiler (line 240)
- Source maps disabled in production (line 237)

**Issues:**
1. **GTM inline script is render-blocking.** While necessary for tracking, it delays First Contentful Paint. Consider loading via `next/script` with `strategy="afterInteractive"`.
2. **11 `<script>` tags** visible in the rendered head for JS chunks. This is normal for Next.js but indicates a moderate bundle size.
3. **`web-vitals` tracking** is enabled in the root layout (`<WebVitals />`), adding a small amount of JS overhead on every page.

### 4.3 Font Loading

**Status:** Good

- Two Google Fonts loaded: Outfit (sans) and Merriweather (serif)
- Both use `display: 'swap'` (prevents invisible text during load)
- Both use CSS variable injection (`--font-outfit`, `--font-merriweather`)
- Fonts are preloaded in the rendered HTML (visible as `<link rel="preload" as="font">`)

**No issues found.**

### 4.4 Caching

**Status:** Mixed

- **Static assets** (`_next/static/*`): 1-year immutable cache -- correct
- **Images** (`/images/*`): 1-year immutable cache -- correct
- **robots.txt**: 24-hour cache -- acceptable
- **HTML pages**: `cache-control: public, max-age=0, must-revalidate` (homepage) or `private, no-cache, no-store` (dynamic pages like `/sunday-lunch`) -- correct for Next.js ISR
- **Sunday lunch page** has `revalidate = 120` (2 minutes) -- appropriate for menu data

**Issue:** The homepage uses `revalidate = 60 * 60 * 24` (24 hours) which means menu changes, hour changes, or event updates won't appear for up to a day. Consider reducing to 1-4 hours for freshness.

## 10. Systems-Level Observations

Several issues found in this audit are **systemic rather than page-specific**:

1. **`keywords` meta tag** -- present on 89 files. A codebase-wide removal is needed, not page-by-page.
2. **BreadcrumbList schema** -- deployed on only 27/100+ pages. A template-level wrapper component that auto-generates breadcrumbs from the URL path would solve this once for all pages.
3. **Canonical tags** -- present on most pages but the pattern is manual (each page sets its own). A centralised canonical generator based on route would prevent future omissions.
4. **Duplicate viewport** -- affects every page due to being in the root layout. Single-line fix.
5. **AI crawler blocking** -- affects entire site. Single Cloudflare setting change.

The highest-leverage fixes are template-level changes: fixing the viewport duplication (1 line, all pages), deploying breadcrumbs site-wide (1 component, all pages), and unblocking AI crawlers (1 setting, all pages). These three changes alone affect 100% of the site's pages.
