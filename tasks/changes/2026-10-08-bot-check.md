## What changed

### 1. The security check fits a narrow phone (LS-004, LS-005)

Cloudflare's wide widget is never narrower than 300px. A 320px phone has 288px inside the page gutters and less inside a padded card, and `<body>` hides sideways overflow, so the widget dragged the form past the edge of the screen where it could not be reached.

- `components/security/TurnstileField.tsx` measures the room its slot has before the widget mounts and renders the compact widget (150px by 140px) under 300px, the wide one otherwise. Decided once per mount, never on resize or rotation: a new size is a new widget and the visitor's token goes with the old one. A slot that cannot be measured, or measures 0, gets the wide widget as before. The widget is never left out.
- The slot holds 65px from the first paint, so nothing moves for anyone who gets the wide widget.
- `components/PrivateHireQuickEnquiry.tsx`: `p-3` below 640px, `p-6` from there up, so a 360px phone keeps the wide widget (302px of room).
- The 9px left on /cash-bingo and /music-bingo at 320px (LS-005) was the form's own submit button: "Book your places" at the large size needs 237px on one line and the booking card leaves 212px. It now takes the Button `wrap` variant from PR #204, which drops its side padding to 16px below 640px. The label still sits on one line. The grid item was not given `min-w-0`: with the button fixed there was nothing left pushing it wide.

The same pages opened at 320px have nothing cut off. Somebody who turns a phone upright after the form has loaded, or zooms a desktop page to 400% after it has loaded, gets the same 22px.

### 2. The careers form stops forwarding its token (WP-012, MG-015)

`app/api/enquiry/recruitment/route.ts` copied the applicant's `turnstile_token` into the form it sends to the management app. The rule since the August 2026 split brain is that a website token is never forwarded: the two apps hold different widgets, so the website verifies the token with its own secret and authenticates upstream with the API key. This was the last route still doing it.

- Forwarding removed, with the unused `originalFormData` parameter. Verification in `checkSpamProtection` is untouched.
- `tests/api/recruitment-enquiry-proxy.test.ts`: no token in any field, header or retry; no token gives 403 and no request to anyone; a token Cloudflare refuses, or Cloudflare unreachable, gives 403 with the phone number and no upstream call; management API down with the fallback email failing, or no fallback mailbox, gives the applicant a 500. Three of them fail when the forwarding line is put back. The finding also suggested adding the route to `tests/api/event-turnstile-forwarding.test.ts`; the same assertions live in the route's own suite instead.

Paired repository: no change needed for this. The management route reads a token only when the caller sends no API key, and the website always sends one.

### 3. A security check that never loads is explained on every form (WP-008)

Every form disables its submit button until Cloudflare hands over a token. A widget blocked by an extension or a works network calls nothing back, so on seven of the eight forms the guest was left with a dead grey button and nothing on screen to explain it. Only the event booking form waited ten seconds and then said something.

- `components/security/TurnstileField.tsx` now runs that ten second clock itself, from mount, after an expiry and after a retry. If no token arrives it shows, in a live region that is on the page from the start: "Security check not completed", "Our security check has not finished, so we cannot take this online yet. Everything you have typed is still here.", "Call 01753 682707 and we will help." with the number as a link, and a "Try the security check again" button.
- A form gets this by mounting the widget. No form was edited for it: the full table form (three placements), the quick sheet, both private hire forms, both Christmas forms and the job form all inherit it.
- The event booking form keeps its own panel (`showInlineError={false}`) and now takes the delay and the heading from the shared widget, so there is one figure and one heading.
- The two failure messages said "we will book this for you" on the enquiry and job forms, where nothing is being booked. They now say "we will help".
- An unsupported browser was shown a "Try Again" button that could only fail again. It now gets the message and the number only.
- An expired token is still replaced quietly. The panel appears only if no replacement turns up within ten seconds.

The button stays disabled without a token and the server still verifies every token. This is a way out for the guest, not a way round the check.

### 4. The "complete the security check" message carries the phone number

`lib/turnstile.ts` answered a submission with no token "Please complete the security check before submitting." and nothing else. It now ends "If it will not load, call 01753 682707 and we will help." One constant, `SECURITY_CHECK_REQUIRED_MESSAGE` in `lib/guest-error-messages.ts`, used by the server and by the two forms that say the same thing themselves (the job application and the short private hire enquiry).

### 5. One rate limiter (WP-006)

`lib/rate-limit.ts`, new. It replaces the two separate in-memory counters in `lib/spam-protection.ts` and `app/api/customers/lookup/route.ts`.

- It counts by the visitor's own address: `cf-connecting-ip` first, `x-forwarded-for` second. Behind Cloudflare, Vercel overwrites `x-forwarded-for` with the address that connected to it, which is Cloudflare's, so unrelated guests were sharing one allowance.
- A refusal is a 429 with a `Retry-After` header and `Cache-Control: private, no-store`. The form limiter's 429 had no `Retry-After`.
- It fails open: a request whose address cannot be read, or a fault inside the limiter, is let through and logged. A limiter must never be the reason a real booking is lost.
- No address is ever logged. A refusal logs the name of the bucket only, at most once a minute for each bucket.
- It is per server. A limit of 5 a minute is 5 a minute from each running copy of the site. That is owner decision 13, and the file says so at the top. Turnstile is still the check that stops bots on the forms.

Unchanged: form submissions are 5 a minute and the phone lookup is 6 a minute, as before. A limited lookup still answers with the degraded "not known" result and not a 429, because the booking form carries on without it.

### 6. Limits on the routes that had none (WP-006, PY-008)

| Route | Limit for one address |
|---|---|
| `POST /api/parking/payment/create-order` | 10 an hour, and 10 an hour for one mobile number |
| `POST /api/table-bookings/paypal/create-order` | 10 an hour |
| `POST /api/event-bookings/paypal/create-order` | 10 an hour |
| `GET /api/parking/availability` | 20 a minute |
| `GET /api/parking/bookings/[id]` | 20 a minute |
| `POST /api/events/[id]/availability` | 20 a minute |
| `GET /api/table-bookings/periods` | 20 a minute |
| `GET` and `DELETE /api/table-bookings/[reference]` | 20 a minute each |
| `POST /api/tracking/booking-conversion` | 20 a minute |
| `POST /api/analytics`, `POST /api/web-vitals` | 60 a minute each |

The figures for reads and payments are the workspace standard's (`rate-limiting.md` section 2 and `payment-processing.md` section 8). The beacons get 60 because one page sends several.

A refused request sends nothing to the booking system, PayPal, Google or CheersAI. On anything a guest sees, the 429 carries 01753 682707: "Too many attempts. Please wait a minute and try again, or call 01753 682707." for forms and reads, and "Too many attempts. Please try again later, or call 01753 682707 and we will sort it out over the phone." at a payment step, where the window is an hour.

Deliberately not limited:

- The three routes that take a payment the guest has already approved in PayPal (`capture`, `capture-order`). Refusing a capture would leave money approved and no booking.
- `GET /api/parking/rates`. The edge stores it for a minute, so it rarely reaches the key.

## Not done on the website, and why

- A shared store for the limits (Upstash), which WP-006 and PY-008 both recommended. Owner decision 13 is no.
- A bot check on `POST /api/parking/payment/create-order` (PY-008). The route is built to be called twice safely, a token can be spent once, and the parking form has no widget, so this is a change to the payment journey that needs the widget added and reset between presses. It is not a safe change to make without a real parking payment being tried end to end, which only the owner can do (decision 9). The per-address and per-number limits above are in place meanwhile.
- A cap on the date range `GET /api/parking/availability` accepts (PY-008). The site sells monthly parking and neither app defines a longest stay, so any cap would be an invented business rule.
- Switching on the interview booking page's bot check. The spec excludes it.

## Assumptions

- The live site is always reached through Cloudflare, so `cf-connecting-ip` is set by Cloudflare and not by the caller. A request sent straight to the Vercel address could set that header itself and avoid the count; it would still have to pass Turnstile on any form.
- A request with no readable address is let through. It used to share one bucket called "unknown". On Vercel an address is always present.
- Guests on the pub's own wifi share one address, so on each route they share its 20 reads a minute and 10 payment orders an hour, on each running copy of the site. A refused read or payment shows the phone number.
- Ten seconds is the wait the event form has used since it was built.
- A widget that a form resets after a submission does not restart the clock. A form that has just been sent may have cleared its fields, and "everything you have typed is still here" would then be untrue. A failed challenge after a reset still shows its own message at once.
- 300px is Cloudflare's documented minimum for the wide widget and 150px by 140px its compact size.
- The website never calls the management recruitment route without an API key: the code returns before the call when the key is missing, and a test pins the header.
