# Turned-away bookings are counted, and the two systems disagreeing is a failure, 26 October 2026

Branch `fix/job-alerts-turned-away-logging`. Release 19 of the customer bookings review (AMS repo, `docs/reviews/2026-10-24-customer-bookings-review.md`), approved by the owner. Needs the AMS side of the same release live first (`POST /api/website/booking-funnel` and its migration); until then every report the website sends is answered with an error, which it logs as one `[write-failure-alert]` line and otherwise ignores.

## Commit 1: every refusal and failure is counted (BK-101)

- [x] `reportFailure` now also sends each report's codes to the management app (`lib/booking-funnel-report.ts`, live site only, 1.5 second limit, run alongside the alert email). The management app keeps one row per report and emails the manager inbox ONE summary a day (owner decision D17), and its table bookings reports page shows the weekly funnel. Codes only: route, refused or failed, status, reason, the booking system's code and the stripped page path. No name, number, email, reference or typed text.
- [x] This narrows the rule in `2026-10-07-failures-are-told-and-reported.md`: a refusal is still never emailed one by one, but it is now counted. One exception becomes a failure: the booking system answering `VALIDATION_ERROR`, `PRICE_CHANGED` or `BOOKING_QUESTIONS_CHANGED` on the table booking, event booking or waitlist route, for details the website had already checked and passed (`answeredByBookingSystem`). The two systems disagree, so every guest may be turned away the same way; it is logged as `CONTRACT_DRIFT` and emails the manager under the usual ten-minute limit, with its own subject. The guest's answer is unchanged. Parking (which hands detail checks to the guest on purpose) and the payment routes (which have their own alert and text) are left out.
- [x] The website's own refusals are reported: the table booking route's detail, outside-hours and screening refusals, the waitlist and private hire enquiry detail refusals, and in `checkSpamProtection` the honeypot, timing and security check refusals for every form, with the page. `verifyTurnstileToken` says why a token failed (`SECURITY_CHECK_MISSING`, `_REJECTED`, `_UNAVAILABLE`, `TURNSTILE_SECRET_MISSING`).
- [x] One `[availability-answer]` line per availability answer: complete, unknown or error, times offered, party size, days ahead, drinks only, and the public reason when nothing was offered. `console.warn`, because the build strips `console.log` and `console.info`.
- Left: rate-limited answers (429) are not counted, so a flood cannot become a flood of reports. The Christmas enquiry route's own detail refusals are not reported here because release 7 is changing that route; its spam and security check refusals are.

## Commit 2: the event booking form's signals and the test key (BK-191, BK-193)

- [x] The event booking form sends a beacon when it is opened, when booking is pressed, when it was blocked before sending (missing details, a security check that could not finish, the booking system's refusal, or the connection) and when a booking went through (`lib/booking-form-signal.ts`, `POST /api/booking-form-signal`). Codes only, no cookie or storage, so it runs whatever the visitor chose about analytics. Each signal is one `[booking-form-signal]` log line and a count in the management app, shown in the daily summary: "opened 40, pressed 0" is a broken form.
- [x] The CI accessibility audit reads `ANCHOR_API_KEY_CI` instead of the live website key, so the booking system can tell test traffic from guests. Until that secret exists the audit is skipped with a notice.
