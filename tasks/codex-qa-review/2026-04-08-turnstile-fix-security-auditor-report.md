**Findings**
- `SEC-001` High: `/api/event-bookings` and `/api/event-waitlist` disable local Turnstile verification but never forward the token upstream. The skip happens at [app/api/event-bookings/route.ts#L128](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/event-bookings/route.ts#L128), [app/api/event-waitlist/route.ts#L103](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/event-waitlist/route.ts#L103), and the shared verifier is only invoked when `skipTurnstile` is false at [lib/spam-protection.ts#L135](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/spam-protection.ts#L135). The outbound proxy headers omit `x-turnstile-token` at [app/api/event-bookings/route.ts#L145](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/event-bookings/route.ts#L145) and [app/api/event-waitlist/route.ts#L120](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/event-waitlist/route.ts#L120). Result: a direct caller can hit both endpoints without solving CAPTCHA.

- `SEC-002` High: `/api/customers/lookup` is an unauthenticated customer-enumeration endpoint and also puts phone numbers in the URL. The handler accepts any `phone` over GET at [app/api/customers/lookup/route.ts#L44](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/customers/lookup/route.ts#L44) and [app/api/customers/lookup/route.ts#L54](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/customers/lookup/route.ts#L54), proxies that to the management API at [app/api/customers/lookup/route.ts#L68](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/customers/lookup/route.ts#L68), and returns the parsed upstream body largely verbatim at [app/api/customers/lookup/route.ts#L79](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/customers/lookup/route.ts#L79) and [app/api/customers/lookup/route.ts#L99](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/customers/lookup/route.ts#L99). Anyone who can guess phone numbers can probe for existing customers and collect whatever profile fields upstream returns.

- `SEC-003` High: The rate limits meant to protect the shared API key are easy to bypass and are not deployment-wide. Both implementations use process-local `Map`s at [lib/spam-protection.ts#L5](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/spam-protection.ts#L5) and [app/api/customers/lookup/route.ts#L10](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/customers/lookup/route.ts#L10), keyed off the first `x-forwarded-for` value at [lib/spam-protection.ts#L9](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/spam-protection.ts#L9) and [app/api/customers/lookup/route.ts#L49](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/customers/lookup/route.ts#L49). Attackers can rotate/spoof forwarded IPs to evade limits, and each instance/cold start gets a fresh counter set. Unique spoofed IPs also grow the Maps without eviction.

- `SEC-004` Medium: `/api/enquiry/open-mic` has no effective CAPTCHA path, and its honeypot is wired to the wrong field name. The route disables local Turnstile at [app/api/enquiry/open-mic/route.ts#L29](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/enquiry/open-mic/route.ts#L29) but never forwards a Turnstile header in the upstream call at [app/api/enquiry/open-mic/route.ts#L43](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/enquiry/open-mic/route.ts#L43). It also accepts `honeypot` in the payload schema at [app/api/enquiry/open-mic/route.ts#L8](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/enquiry/open-mic/route.ts#L8), while the shared spam check only blocks `website` or `honeypot_field` at [lib/spam-protection.ts#L107](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/spam-protection.ts#L107). Bots can fill the hidden field and still be proxied upstream.

- `SEC-005` Low: The remaining spam heuristics are trivial to spoof. `_t` is accepted as any client-supplied number at [lib/spam-protection.ts#L124](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/spam-protection.ts#L124), so a bot can just send `_t: 999`. The phone-country filter only runs when the value starts with `+` at [lib/spam-protection.ts#L70](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/spam-protection.ts#L70) and [lib/spam-protection.ts#L73](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/spam-protection.ts#L73), so local-format numbers bypass it entirely. These are fine as noisy heuristics, not as a primary control.

**Assumptions**
- I did not review the upstream management API, so the Turnstile findings assume these proxy routes are responsible for passing the token contract through.
- If your edge layer rewrites `x-forwarded-for` to a trusted value before Next.js sees it, spoofing impact drops, but the in-memory, per-instance limiter weakness remains.

No comparable Turnstile-forwarding gap stood out in [app/api/table-bookings/route.ts#L376](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/table-bookings/route.ts#L376), [app/api/table-bookings/route.ts#L385](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/table-bookings/route.ts#L385), [app/api/public/private-booking/route.ts#L136](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/public/private-booking/route.ts#L136), and [app/api/public/private-booking/route.ts#L144](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/api/public/private-booking/route.ts#L144); those two routes at least pass the token upstream as intended.
