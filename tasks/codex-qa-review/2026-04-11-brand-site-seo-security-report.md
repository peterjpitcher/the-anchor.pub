- Medium-high: The spec’s stale-redirect and related-events logic depends on `anchorAPI.getEvents()`, but that client silently swaps to synthetic fallback events on API failure in `lib/api/client.ts` [client.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/api/client.ts:812) and [client.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/api/client.ts:1386). The fallback payload is a made-up generic event in `lib/api/events.ts` [events.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/api/events.ts:338). If you use that for 301 decisions or “related events”, an outage can produce wrong permanent redirects or fake related cards.
- Medium: The current event route turns any `getEvent` failure into a permanent redirect to `/whats-on` in `app/events/[id]/page.tsx` [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:204). That is a real integrity risk already: a transient upstream failure can emit a permanent redirect for a valid event URL. Adding more 301 logic increases the same cache/SEO poisoning risk.
- Medium: Current video embed handling is too trusting. In `app/events/[id]/page.tsx` it treats any URL containing `youtube.com` or `youtu.be` as embeddable and rewrites it with string replacement [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:624). That allows arbitrary non-YouTube URLs with those substrings to be iframed.
- Medium: The page assumes a well-formed event object and directly dereferences nested fields like `event.location.name` and `faq.acceptedAnswer.text` in `app/events/[id]/page.tsx` [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:566) and [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:609). There is no route-level error boundary in `app/events/[id]/`, so malformed API data can break the whole page.
- Low: `previous_event_summary` and `attendance_note` would be rendered as plain first-party assertions, just like current event copy in `app/events/[id]/page.tsx` [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:547). That is not XSS, but it is a misleading-content risk because nothing in the UI marks those claims as unverified.

**Direct Answers**
1. `cancellation_policy` and `accessibility_notes`: low XSS risk if rendered like current event content. The event page uses React text nodes/attributes, not HTML injection, for descriptions, FAQs, and image alts in `app/events/[id]/page.tsx` [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:550), [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:608), [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:373). The only `dangerouslySetInnerHTML` on the event route is JSON-LD via `components/seo/EventSchema.tsx` [EventSchema.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/components/seo/EventSchema.tsx:13), and it escapes `<` in `lib/jsonld.ts` [jsonld.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/jsonld.ts:1).
2. 301 stale past events: not an open-redirect problem if targets stay site-relative and encoded like the current canonical redirect in `app/events/[id]/page.tsx` [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:212). The real risks are extra lookup load and, more importantly, wrong redirects if `getEvents()` falls back to synthetic data. Same-query load is somewhat damped by server fetch revalidation in `lib/api/client.ts` [client.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/api/client.ts:720).
3. `previous_event_summary` and `attendance_note`: yes, they would read as verified fact unless you label them otherwise. This is a content governance issue, not a code injection issue.
4. Meta keywords: no XSS concern. Malicious keywords can still spam the page’s metadata and hurt SEO quality/trust. This should be validated, deduped, and length-limited.
5. `image_alt_text`: React escapes attribute values by default, so HTML/script in alt text becomes literal text, not executable code.
6. LiteYouTube: safe only if it uses `new URL()`, an allowlist of YouTube hosts, and a strict 11-character video ID regex. If it follows the current substring-based approach, URL injection remains a real risk.
7. Related events: yes, unexpected API data can break rendering if the new section is inlined into the page. The safer existing pattern is a separate server component with its own `try/catch` fallback, like `components/UpcomingEvents.tsx` [UpcomingEvents.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/components/UpcomingEvents.tsx:7) and [UpcomingEvents.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/components/UpcomingEvents.tsx:153).
8. API failure handling today: no route error boundary; `generateMetadata` falls back to “Event Not Found” metadata on error in `app/events/[id]/page.tsx` [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:193), and the page itself permanently redirects on fetch failure [page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:204). There is fallback UI elsewhere in the codebase, but not on the event detail route.

The real issues are redirect integrity, fallback data being treated as authoritative, and weak video URL validation. The XSS concerns around the new text fields are mostly theoretical in the current render model unless someone introduces `dangerouslySetInnerHTML` for those fields.
