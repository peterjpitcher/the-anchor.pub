**Architecture Summary**
- Event listings point users at event detail pages, not category pages. The detail route is still the main entry point for event URLs.
- On the detail route, the current redirect chain is: fetch failure -> `/whats-on`; non-canonical segment -> canonical `/events/{slug||id}`; draft -> 404; stale past event with a valid next event in the same category -> 301 to that next event page.
- The removed behavior is specifically the old “stale past event with no next event -> redirect to category page” fallback. In current code, that path now renders the existing event page.
- The rendered stale page still gets past-event UX from separate logic: `getStatusNotice()` shows the ended/cancelled alert, and `getEventBookingBlockReason()` disables booking. The helper’s `showEndedBanner` is not what drives the banner.
- `generateMetadata()` separately noindexes stale/cancelled pages using duplicated date/status checks, and `app/sitemap.ts` separately removes older event URLs from the sitemap. Category pages remain linked from the event page, but are no longer part of the redirect path.

**Risks Found**
- Thresholds are inconsistent at the exact boundary. `getEventSeoStrategy()` treats `30` days old as stale/noindex and `7` days old cancelled as noindex because it uses `<` checks ([helper]( /Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/event-seo-strategy.ts:50)), while `generateMetadata()` and `app/sitemap.ts` only flip at `> 30` and `> 7` ([metadata](</Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:171>), [sitemap]( /Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/sitemap.ts:239)). That means exact-boundary pages can be “stale” by helper logic but still indexable and still present in the sitemap.
- `getEventSeoStrategy()` is not the single source of truth. The page consumes only `redirect`; `index`, `showEndedBanner`, and `stage` are ignored in the consumer ([page](</Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:255>)). Banner behavior and robots behavior are duplicated elsewhere, which is already drifting.
- Cancelled events still trigger the “find next upcoming event in category” lookup even though the helper’s cancelled branch never redirects ([page](</Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:243>), [helper]( /Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/event-seo-strategy.ts:50)). That is wasted I/O and the page comment “redirect stale past/cancelled events” is now misleading.
- The docs still describe the removed category fallback redirect, so repo documentation no longer matches runtime behavior ([spec]( /Users/peterpitcher/Cursor/OJ-The-Anchor.pub/docs/superpowers/specs/2026-04-11-event-page-seo-optimisation-design.md:123), [plan]( /Users/peterpitcher/Cursor/OJ-The-Anchor.pub/docs/superpowers/plans/2026-04-11-event-page-seo-optimisation.md:170)).
- There are no direct tests for `getEventSeoStrategy` in `tests/`, so the redirect/noindex boundary behavior is unprotected.

**Recommendations**
- Make lifecycle state a single shared source of truth for redirect, robots, and sitemap inclusion. Right now the helper, metadata, and sitemap each reimplement overlapping rules.
- Decide the exact cutoff semantics explicitly and align them everywhere: either `>= 30` / `>= 7` or `> 30` / `> 7`, but not both.
- Skip the category-upcoming lookup for cancelled events unless cancelled redirects are intentionally coming back.
- Add direct tests for: active, recent past, stale with next event, stale with no next event, cancelled under threshold, cancelled at threshold, cancelled over threshold, and exact 30/7 day boundaries.
- Update the plan/spec docs if the category fallback removal is intended to be permanent.
