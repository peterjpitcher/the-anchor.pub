# Assumption Breaker Report

The spec is not uniformly wrong, but it overstates confidence in several places, conflates crawl blocking with index blocking, and misses a few repo-specific risks. The weakest items are Issue 4, Issue 3, and the blanket `<3 posts` rule for blog tags.

## 1. CSS Blocked by `robots.txt`
- **What the spec claims:** `/*?dpl=*` is blocking CSS, so adding `Allow: /_next/static/` fixes the critical rendering issue. See [docs/gsc-coverage-fix-spec.md](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/docs/gsc-coverage-fix-spec.md:15).
- **What the codebase actually shows:** [app/robots.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/robots.ts:7) does disallow `/*?dpl=*`, and [next.config.js](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/next.config.js:130) also sets `X-Robots-Tag: noindex, nofollow` on `/_next/static/:path*`, `/(.*).js`, and `/(.*).css`.
- **Verdict:** **Incomplete, not fully wrong.** Google’s docs separate these concerns: `robots.txt` controls crawlability, while `X-Robots-Tag: noindex` controls indexability and only works if the resource is crawlable. So the current GSC label `Blocked by robots.txt` is consistent with the `/*?dpl=*` rule, not the header. If production CSS URLs really carry `?dpl=...`, an allow rule can fix the blocked-resource problem while keeping the noindex headers. The overreach is claiming the root cause is fully proven from the repo alone; the `?dpl=` injection itself is deployment/runtime behavior, not codebase behavior.
- **Recommended correction:** Keep the `X-Robots-Tag` headers. Reword the spec to say: if sampled blocked CSS URLs in GSC are same-host `/_next/static/...?...dpl=...`, then `/*?dpl=*` is the blocking rule and an allow rule inside the existing `User-agent: *` group is appropriate. Also note that Google uses rule specificity, not file order, for precedence.

Only reopen it as a code task if a live reference is found.

## 3. OG Image Routes
- **What the spec claims:** Add `*/opengraph-image` to `robots.txt`; social crawlers “typically ignore robots.txt,” so previews will still work. See [docs/gsc-coverage-fix-spec.md](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/docs/gsc-coverage-fix-spec.md:90).
- **What the codebase actually shows:** The OG route already returns `X-Robots-Tag: noindex, nofollow, noimageindex` in [app/events/[id]/opengraph-image.tsx](</Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/opengraph-image.tsx:147>), and event metadata points `og:image` directly at that route in [app/events/[id]/page.tsx](</Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/events/[id]/page.tsx:163>).
- **Verdict:** **Wrong and risky.** Google’s own docs say image URLs must remain crawlable for `X-Robots-Tag noindex` to be seen. X’s official Cards docs explicitly say Twitterbot respects robots.txt and that if an image URL is blocked, no thumbnail is shown. The spec’s social-crawler claim is therefore unsafe. Also, `*/opengraph-image` is malformed for Google-style path rules because it does not start with `/`.
- **Recommended correction:** Do not add a blanket robots disallow here. Keep the existing response headers. If you want to reduce Google image crawling, treat that as a measured tradeoff and, if necessary, create crawler-specific rules rather than blocking the same URL used for `og:image`.

## 4. Booking Wizard State URLs
- **What the spec claims:** Add `Disallow: /book-table?*`; this is only a crawl hint and won’t break anything important. See [docs/gsc-coverage-fix-spec.md](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/docs/gsc-coverage-fix-spec.md:154).
- **What the codebase actually shows:** The canonical is `/book-table` in [app/book-table/page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/book-table/page.tsx:28), but the page also reads `searchParams` for prefill state in [app/book-table/page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/book-table/page.tsx:33). The site itself links to these variants, for example [app/halloween/page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/halloween/page.tsx:14), [app/sunday-lunch/page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/sunday-lunch/page.tsx:17), and [app/fathers-day/page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/fathers-day/page.tsx:22). Also, `parsePurpose()` only accepts `food` or `drinks` in [app/book-table/page.tsx](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/book-table/page.tsx:51), so `?purpose=sunday_lunch` is not even valid state.
- **Verdict:** **Incomplete and somewhat self-defeating.** Google does support query matching in robots rules, so `/book-table?*` would match parameterized variants. But Google also says not to use `robots.txt` for canonicalization. Blocking these URLs prevents recrawl of the variants, which means Google can no longer see the canonical on those duplicates. Since GSC already labels them “Alternative page with proper canonical,” the current canonical setup is working. The deeper issue is that the site itself generates these URLs, and some are invalid.
- **Recommended correction:** Fix the internal link patterns first and normalize invalid params like `purpose=sunday_lunch`. If crawl suppression is still needed afterward, describe it as a tradeoff separate from canonicalization, not as a harmless hint.

## 6. Blog Tag Pages
- **What the spec claims:** Noindex any tag page with fewer than 3 posts because those pages are thin. See [docs/gsc-coverage-fix-spec.md](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/docs/gsc-coverage-fix-spec.md:218).
- **What the codebase actually shows:** Zero-post tags already redirect in [app/blog/tag/[tag]/page.tsx](</Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/blog/tag/[tag]/page.tsx:66>). The page currently has no `robots` noindex in `generateMetadata()` at [app/blog/tag/[tag]/page.tsx](</Users/peterpitcher/Cursor/OJ-The-Anchor.pub/app/blog/tag/[tag]/page.tsx:36>), but these pages are not just bare archives: they render hero and intro copy from [lib/tag-seo-content.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/tag-seo-content.ts:36). Some low-count tags are clearly intentional, curated landing pages, including `food` at [lib/tag-seo-content.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/tag-seo-content.ts:75), `parking` at [lib/tag-seo-content.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/tag-seo-content.ts:108), and `entertainment` at [lib/tag-seo-content.ts](/Users/peterpitcher/Cursor/OJ-The-Anchor.pub/lib/tag-seo-content.ts:343). I counted 21 published tags; 8 currently have only one post.
- **Verdict:** **Wrong or at least unearned.** Post count alone is not a valid thin-content proxy in this repo because some 1-post tags are deliberate SEO pages with bespoke copy and strategic intent.
- **Recommended correction:** Do not use a blanket `<3 posts` threshold. If tag pruning is needed, make it conditional on low-value fallback tags, not low count alone, and review those tags manually. The 0-post case is already handled correctly.
